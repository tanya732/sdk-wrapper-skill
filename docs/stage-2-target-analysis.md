## Target Framework: Play Framework 2.8 (Java)

### Key Concepts

- **Middleware:** Implemented as `Action` or `Filter` classes.
- **Request/Response:** `play.mvc.Http.Request`, `play.mvc.Result`
- **Configuration:** Typically via `application.conf` or DI
- **Headers:** Accessed via `request.header("Authorization")`, etc.
- **Request Context:** Can attach attributes to `Request` for downstream access

## Mapping: Core SDK → Play Middleware

| Core SDK Concept                | Play 2.8 Mapping                        |
| ------------------------------- | --------------------------------------- |
| `AuthOptions`                   | Config object, loaded via DI/conf       |
| `AuthClient.verifyRequest(...)` | Called in a custom `Action` or `Filter` |
| Headers map                     | Extracted from `Request`                |
| `HttpRequestInfo`               | Built from Play `Request`               |
| `AuthenticationContext`         | Claims attached to request attrs        |
| Exceptions                      | Return 401/403/400 as appropriate       |

## Recommended Wrapper Design

- **Class:** `Auth0JwtAction` (extends `Action.Simple`)
  - Reads config (domain, audience) from DI or constructor
  - Extracts `Authorization` (and optionally `DPoP`) headers
  - Builds `HttpRequestInfo` from Play `Request`
  - Calls `authClient.verifyRequest(headers, requestInfo)`
  - On success: attaches claims to request attrs, calls delegate
  - On failure: returns error response (401/403/400)

- **Usage:**
  - Annotate controller/actions with `@With(Auth0JwtAction.class)`
  - Claims available via `request.attrs().get(...)`

## Example Usage

```java
@With(Auth0JwtAction.class)
default Result protectedEndpoint(Http.Request request) {
    AuthenticationContext ctx = request.attrs().get(Auth0JwtAction.AUTH_CONTEXT);
    String user = (String) ctx.getClaims().get("sub");
    return ok("Hello, user: " + user);
}
```

## Notes

- All validation is synchronous (blocking)
- Play’s default thread pool is sufficient for blocking calls
- Error handling should map SDK exceptions to HTTP status codes
