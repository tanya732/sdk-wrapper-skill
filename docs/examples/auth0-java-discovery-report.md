## Architecture Summary

The auth0-auth-java SDK v3.0.0 is a **dual-architecture** client library providing two major API clients:

1. **AuthAPI** — Handwritten client for Auth0's Authentication API. Handles login, signup, password reset, MFA, passwordless, token exchange, and OAuth flows. Uses the `Request<T>.execute().getBody()` pattern for synchronous HTTP calls via OkHttp.

2. **ManagementApi** — Fern-generated client for Auth0's Management API. Provides 30+ sub-clients (users, clients, connections, organizations, roles, etc.) with both synchronous and async variants. Uses direct return values and a hierarchical sub-client architecture with memoized lazy initialization.

This dual nature is the **most important architectural observation** for wrapper SDK design — the two halves have fundamentally different patterns, error hierarchies, and usage conventions.

## Design Patterns

### Builder Pattern (Staged)

Both clients use the Builder pattern with staged interfaces:

```java
// AuthAPI: AuthAPI.newBuilder() returns Builder with required stages
AuthAPI.newBuilder(domain, clientId, clientSecret) // NameStage → _FinalStage
    .withOrganization(orgId)                        // optional
    .build();

// ManagementApi: ManagementApi.builder() with required stages
ManagementApi.builder()
    .domain(domain)            // DomainStage
    .token(token)              // or .clientCredentials(id, secret)
    .build();                  // _FinalStage
```

### Memoized Lazy Initialization (Sub-clients)

ManagementApi creates sub-clients lazily using `Suppliers.memoize()`:

```java
private final Supplier<UsersClient> usersClient =
    Suppliers.memoize(() -> new UsersClient(...));

public UsersClient users() {
    return this.usersClient.get();
}
```

### Immutable Types

All model types are immutable with Jackson deserialization via builders:

```java
@JsonDeserialize(builder = User.Builder.class)
public final class User {
    private final String userId;
    private final Optional<String> email;
    // No setters, only getters
}
```

### Request Pipeline (AuthAPI)

AuthAPI uses a `Request<T>` pipeline:

```
Method call → Request<T> builder
    → .setParameter() (fluent)
    → .execute()
    → Response<T>
    → .getBody() → T
```

### Visitor Pattern (Enums)

Fern-generated enums use Visitor pattern:

```java
connectionType.visit(new ConnectionType.Visitor<Result>() {
    public Result visitDatabase() { ... }
    public Result visitSocial() { ... }
    public Result visitUnknown(String unknownType) { ... }
});
```

## Error Handling

### Dual Exception Hierarchy

**AuthAPI Side:**

```
java.io.IOException
  └── Auth0Exception
        └── APIException
              ├── getStatusCode() → int
              ├── getError() → String
              ├── getDescription() → String
              ├── isMultifactorRequired() → boolean
              ├── isInvalidCredentials() → boolean
              ├── isMultifactorTokenInvalid() → boolean
              ├── isMultifactorEnrollRequired() → boolean
              └── getValue(key) → Object
```

**ManagementApi Side:**

```
java.lang.RuntimeException
  └── ManagementException
        └── ManagementApiException
              ├── statusCode() → int
              ├── body() → Object
              ├── headers() → Map<String, Object>
              └── Specific subclasses:
                    ├── BadRequestError (400)
                    ├── UnauthorizedError (401)
                    ├── PaymentRequiredError (402)
                    ├── ForbiddenError (403)
                    ├── NotFoundError (404)
                    ├── ConflictError (409)
                    ├── PreconditionFailedError (412)
                    ├── TooManyRequestsError (429)
                    ├── InternalServerError (500)
                    └── ServiceUnavailableError (503)
```

**Critical Observation:** AuthAPI exceptions are **checked** (extend IOException), while ManagementApi exceptions are **unchecked** (extend RuntimeException). A wrapper SDK must handle both paradigms.

## Async/Sync Model

- **AuthAPI:** Synchronous only. `Request<T>.execute()` is a blocking call.
- **ManagementApi:** Provides both sync and async variants:
  - Sync: `mgmt.users().get(id)` — blocking, returns `T`
  - Async: `mgmt.users().async().get(id)` — returns `CompletableFuture<T>` (inferred from Raw client pattern)
- **HTTP Client:** OkHttp with synchronous dispatch by default via `Auth0HttpClient`.

## Key Observations

1. **Dual Architecture is the #1 Challenge.** Any wrapper must present a unified API over two fundamentally different client patterns (Request pipeline vs direct returns, checked vs unchecked exceptions).

2. **Fern Code Generation.** The ManagementApi is generated from an OpenAPI spec using Fern. This means:
   - Very consistent patterns (good for wrapping)
   - Many model types (hundreds of DTOs)
   - Staged builders everywhere
   - The wrapper should NOT re-expose all DTOs — use the core SDK's types

3. **Password as `char[]`.** Security-conscious design — passwords are `char[]` not `String` (can be zeroed). The wrapper must preserve this.

4. **Optional vs OptionalNullable.** The SDK distinguishes between "absent" (not sent) and "explicitly null" using `Optional<T>` and a custom `OptionalNullable<T>`. Wrappers should not lose this distinction.

5. **Token Auto-Refresh.** ManagementApi with `clientCredentials()` automatically manages token lifecycle. A good wrapper should leverage this rather than re-implementing it.

6. **30+ Sub-Clients.** The wrapper doesn't need to expose all 30+ sub-clients initially. A phased approach (auth first, then popular management operations) is recommended.

## Monorepo Notes

**Not a monorepo.** auth0-auth-java is a single-module Maven project. No inter-package dependencies to consider. The wrapper SDK should depend directly on `com.auth0:auth0-auth-java:3.0.0`.
